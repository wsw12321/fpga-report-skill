# 报告结构与写法

范例：`FPGA/exp-1/report.md`（组合逻辑，ALU + 译码器）和 `FPGA/exp-2/report.md`（时序逻辑，定时器 + 数码管扫描）。动笔前先读上一次的报告，沿用它的格式、语气和篇幅（约 550～650 行）。

## 读者与语气

- 读者是批改报告的助教和老师；报告以作者（学生）的第一人称“我”来写。
- 中文，句子短，一句话说一件事。模块名、信号名、文件名、命令用反引号。数字带单位，例如 3.125 ns、10 ms、125 Hz。
- 结论都要有依据：仿真输出、报告数据、RTL 图或照片。凡是写出来的现象和数字，必须是实际看到或跑出来的。
- 设计中发现的问题如实写在“分析”和“可以改进的地方”里，不要回避，也不要夸大。
- 不写“本报告不涉及 ××”之类的免责声明（作者在 Lab 2 中明确反对过）。文档里讲到、但设计中以别的形式体现的概念，写成一项，说明它在设计中对应什么（Lab 2 的写法：寄存器堆 → 设计中各类寄存器 + 读优先 / 写优先的对应）。不要声称实现了没有实现的模块。

## 标题

```markdown
# Lab N report：<实验主题，例如“时序逻辑电路”>

**PB25050921 吴书玮**
```

模板第 3 行的 `PB20111623 马子睿` 是模板作者，不能照抄。模板中 `> 1. 请……` 这些引导语要全部删掉。

## 各节内容

### 实验目的与内容

- 开头一两句：用自己的话说这次做了什么（模板要求不抄 PPT）。
- **必做内容**：编号列表，每项写清功能、接口和验收要求中的关键点。
- **附加内容**：设计中超出要求的功能。从代码、约束文件和 git 提交记录中找，不要漏掉。
- **实验目的**：一段话，说要掌握的知识点和方法。

### 逻辑设计

1. **模块划分与数据通路**
   - mermaid `flowchart LR` 画顶层，复杂模块再单独画一张内部图；
   - “文件 / 模块 / 作用”表；
   - 参数表：表达式、实际取值、含义；
   - 端口与板上资源、引脚对应表，只看 xdc 中未注释的行（`grep -vE '^\s*#'`）。
2. **状态转换**：有显式状态机就画 `stateDiagram-v2`。没有显式状态机，但行为可以抽象成几个状态的（例如计数器的停止 / 计数 / 暂停），也可以画，并注明“设计中没有显式编码的状态机”。
3. **核心代码说明**：编号（1）（2）……，每项包括：
   - 加粗的小标题；
   - 从源码**原样**摘录的代码（可以删掉无关的行，但不改写逻辑，不编造注释里没有的内容）；
   - 几条要点：为什么这样写、与实验文档的提示有什么关系、有什么边界情况。
4. **设计演进**：用 git 提交（短 hash）说明每次改了什么。没有 git 时省略这一项。

### 仿真结果与分析

- 第一句固定写：“下列控制台输出都是用 Vivado 2023.1 的 xsim 对当前源码实际运行得到的，波形图由仿真导出的 VCD 绘制。”
- 仿真文件表（文件 / 说明）。
- 每个 testbench 依次写：
  - 检查方法；
  - 用例表（编号 / 操作 / 检查内容）；
  - 控制台输出：代码块原文，删掉 `$finish` 行里的绝对路径；
  - Vivado 截图，以及截图里各窗口的说明；
  - 波形图，并逐段分析：在什么时间看到了什么，说明了什么。
- “分析”：
  - 检查是否全部通过；
  - 仿真中发现的设计特性或问题（例如 Lab 2 中第一次减一不到 1 s）；
  - 变异测试的结果。

### 电路设计与分析

- **RTL 图**：顶层一张，再加关键子模块。每张图写“图中元件 ↔ 代码”的对应：
  - 用图中的实例名，例如 `q_next_i__0`、`RTL_MUX`、`RTL_REG_SYNC`；
  - 把图中的常数换算成十进制，与代码核对，例如 `0x5F5E0FF` = 99,999,999。
- **资源**：
  - 总表：LUT / FF / Latch / CARRY4 / F7、F8 / BRAM / DSP / IOB / BUFG，数据来自 `*_utilization_placed.rpt`；
  - 分层表；
  - 按代码逐项推算 FF 数，与报告对比；
  - 说明 IO 数由哪些端口组成；
  - 综合与实现的 LUT 差异。
- **时序**：
  - 表（WNS / TNS / WHS / THS / WPWS / 失败端点），数据来自 `*_timing_summary_routed.rpt`；
  - Design Runs 截图及其说明；
  - 最差路径：起点、终点、数据路径延迟（逻辑 / 布线）、逻辑级数，以及对应哪段代码；
  - Methodology 警告的解释；
  - 功耗（来自 `*_power_routed.rpt`）。
- **f_max**：只有把约束收紧到 WNS < 0 时，`1 / (T − WNS)` 才是可靠的估计（lab3 文档的方法）。WNS > 0 时只说“在当前约束下有 x ns 余量”，不要据此推算最高频率。

### 测试结果与分析

- 第一句：上板平台（Nexys4 DDR）和比特流路径。
- 验收步骤表：步骤 / 操作 / 现象。“现象”一栏需要作者确认。
- 每张照片：
  - 先放图；
  - 加粗小标题；
  - 写照片中**看得到**的事实：显示的数值、哪颗灯亮、手指按着哪个键；
  - 再说明这对应验收要求的哪一条。
- 一句话说明板上与设计无关的灯：CPU_RESET 左边的绿灯是 DONE 指示灯（FPGA 已配置），红色的是电源等指示灯。
- “分析”：照片与验收要求的对应关系，以及作者确认过的、照片看不出来的现象（无闪烁、无串显、按键只响应一次等）。

### 总结

- **完成的任务**：带上关键数字，例如检查项数、WNS、LUT 数。
- **收获与体验**：具体到技术点，不写空话。
- **可以改进的地方**：仿真和分析中发现的真实问题，以及具体改法。
- **建议**：可选，语气平和，一两条。交付时告诉作者这部分可以删。

## mermaid 注意事项

- `stateDiagram-v2` 的状态 ID 用 ASCII，显示文字写在描述里：`STOP: 停止 q = 0，td = 1`。
- 转移标签里不要用英文分号 `;`，用中文逗号。
- flowchart 的节点文字用引号包起来，换行用 `<br/>`。在 `<` 后面加一个空格，避免被当成 HTML 标签。
- 同一个节点有多条输入时，分开写多条边，不用 `A & B --> C` 的写法，兼容性更好。
